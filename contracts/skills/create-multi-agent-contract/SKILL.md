# Create a multi-agent contract

Treat the artifact as a **multi-agent skill**: retained guidance plus enforceable coordination. Document roles, message intent, state guidance and outcome meaning, not just schemas. Use ordinary `"..."` or multiline `"""` strings directly above the item they guide. The parser retains them as prompt metadata for the agent, including business rules the room cannot directly enforce. Use `~r` for regular expressions. Other sigils are for cases that need their special behavior; `/* ... */` author comments are ignored by role queries. For runtime rosters, partial collection, offline grace or renewable clocks, read [the current coordination guide](../../spec/multi-agent-skills.md) and its normative links. For runtime participants, use the selected reusable type form: `type reviewer: agent` with ordinary guidance and bounded attributes, then `reviewers: list(reviewer)`. Validate host bindings against that schema and preserve all guidance in agent views. Explain agreed designs directly; compare alternatives only for unresolved choices or when requested. Keep ordinary agents independent of optional client machinery. For partial collections, declare `room.contributions/1`, specify the successful reply, and use standard room contribution controls for terminal outcomes. A member may stop only its own contribution; the host may report terminal execution failure scoped to its session, collection entry and member. Retain the original cause type and evidence reference. Do not author `failure unable()` or infer failure from recoverable errors. Read [contribution outcomes](../../spec/contribution-outcomes.md).

Keep room rules and discovery independent of client implementation. Any authorized
agent can participate directly; the journal/program/LLM replacement runtime is
optional and experimental. Prefer lowercase body keywords, preserving literal contents
and the source pins of running sessions. See [room/client separation](../../spec/room-clients-v2.md)
and [keyword spelling](../../spec/lowercase-v2.md).

Read [the shared authoring reference](../multi-agent-contracts/references/authoring.md). Use [the synthetic chat](../../contract-lab/histories/review-chat.md) and its [derivation](../../contract-lab/histories/review-derivation.md) as a worked example when helpful.

Collect the relevant conversation, participant identities, and intended outcome. Use user-provided history or an already authorized source; retrieve only relevant excerpts. Retain stable message IDs or timestamps in a source-to-rule table. Label synthetic examples. Avoid copying unrelated private conversation into artifacts.

Extract who may offer, accept, submit, review, request changes, accept the result, and cancel. Separate observed actions from obligations: one successful conversation does not prove that other orders are forbidden. Distinguish proposals, refusals, corrections, and accepted decisions. A participant's suggestion rejected later in the conversation must not become a rule.

Identify missing decisions that change observable behavior. Examples include whether all selected participants must respond, any one is sufficient, or the run continues with the available results (`collect` with `room.contributions/1`); whether participants form a runtime roster (`type reviewer: agent` with `reviewers: list(reviewer)`); whether a deadline belongs to a reply, phase or whole run, who can establish completion, and what cancellation means after an external effect. Continue drafting the agreed portion and make unresolved policy explicit. Do not infer success merely from silence, a `DONE` marker, or an artifact identifier.

Write the discovery header and typed body. Place documentation immediately before the declaration it explains using an ordinary quoted one-line or multiline string. State evidence IDs in relevant docs where traceability helps. Keep schema bounds that were not in the source labeled as proposed choices. Use reference bindings for exact offers and submissions; separate authors from reviewers when independence is required.

When a role sends a request and waits for its answer, write the request with reply alternatives: `lead -> reviewer: request() awaits reviewing`, then `=> review(decision=approve) & approved`, `| review(decision=revise) & revising` and `| @5m & stalled` on the following lines. Each reply picks its own next state, the alternatives cover every reply the recipient may send, and the timeout comes last. The reply type declares a `ref` field to the request's kind; the compiler supplies the binding. Never write the request as a plain transition answered by a separate rule in its target state: the compiler refuses that with `reply_required`. Keep a timed rule such as `worker -> lead: deliverable() @1h => delivered | stalled` for an owed report that answers no request. Read [reply alternatives](../../spec/contract-dsl.md#reply-alternatives). Group replies use `each @5m` for every sender or `@5m` for any one; `collect reports from reviewers -> lead @5m => summarizing` continues with the available results ([collections](../../spec/coordination.md)). When an owed message should not leave the state, give the event its own deadline: `event worker -> lead: ack() @5m => stalled`. It is owed once per entry into the state: one accepted event discharges it, it does not re-arm, and it is not a recurring heartbeat. Repeats are accepted but owe nothing. Every contract declares its whole-run clock, such as `contract @30m => expired`; use `contract @infinity => expired` only when the run is deliberately open-ended. A state cap uses the same `@duration` notation on its declaration. Explain when each clock starts, which terminal outcome it selects, and that ordinary progress/retries do not reset it; explicit heartbeat effects are opt-in. Keep response windows inside enclosing caps and use explicit state-entry bounds for repeated work. There is no generic idle timeout.

Create executable scenarios covering the successful conversation and the important counterexamples suggested by the source. For a multiparty workflow, exercise relevant arrival orders, missing participants, wrong-role messages, stale references, duplicate delivery, and timer boundaries. Reuse existing runtime tests for generic behavior instead of duplicating them mechanically.

Compile with the shared helper, query at least the affected role and one documented type, and replay the scenarios. Correct in-scope failures using observed failing and passing checks. Deliver the contract, derivation, scenario results, and unresolved assumptions. Keep starting live participants and publishing messages within the current task's authorization.
