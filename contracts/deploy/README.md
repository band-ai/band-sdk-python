# Building and checking a release

The [operator runbook](OPERATIONS.md) covers live backups, restore, storage
pressure, complete journal retention, and replay that never executes code.
The optional [Band services](BAND-SERVICES.md) package history-based authoring,
refinement and supervised replacement, including their hash-locked dependencies,
credential-file configuration and systemd units.

Build on the same Linux architecture and distribution as the target. The engine
bundle contains Erlang, Elixir libraries, both YAML dependencies and the pinned
Unicode data/license. The target needs Python 3.12 and the native packages in
`requirements-system.json`; it does not need Mix, a compiler, or the source tree.
The canonical `band-sdk` wheel and its `contracts` extra use the SDK dependency
graph. The release seals `requirements-runtime.lock` and its exact wheels under
`dependencies/` for installation without package-index access.

From a clean committed source tree, use Python 3.12 and the selected Elixir/OTP
toolchain, then build into a new directory. `contracts/.tool-versions` pins the reference
Elixir 1.18.4 / OTP 27.3.4.17 pair. Both the builder and CI reject OTP older than
27.3.4.17 or a different major before creating output, and record the full OTP
patch version in their manifests:

```sh
uv sync --all-packages --locked --extra dev --extra contracts --python /usr/bin/python3.12
.venv/bin/python -m contracts.deploy.buildrelease /absolute/new-release
.venv/bin/python -m contracts.deploy.smokerelease /absolute/new-release
```

The build rejects tracked or untracked source changes before creating a release.
It exports the exact commit to a temporary directory, installs the hash-locked
Python build tools into a fresh virtual environment, and resolves Mix dependencies
with `--check-locked`. Build subprocesses receive a limited environment. The
commit timestamp fixes wheel and release-file timestamps; Erlang compilation is
deterministic. The engine release forces distribution off for every entrypoint,
so its cookie file contains an inert reproducible marker, not a runtime credential.
Reproducibility applies to the same source commit and recorded native toolchain.

Run the repeatable CI gate from a clean checkout:

```sh
.venv/bin/python -m contracts.deploy.ci /absolute/new-ci-run
```

Run these module commands from the SDK root. The command above is the complete
manual contract release gate; hosted workflow status must be checked separately
in the SDK's [CI documentation](../../docs/ci-cd-workflows.md). It selects BEAM
from `contracts/.tool-versions` and needs Node 24 for specification checks and
Linux Python 3.12. The callback sandbox requires Python under `/usr`; a
tool-cache Python is not compatible. Provision bubblewrap and libseccomp before
running the gate. No model-provider credentials are needed, and the gate does
not promote a release automatically.

On Ubuntu with AppArmor's unprivileged user-namespace restriction enabled, the
launcher also needs an executable-specific namespace profile. The repository provides
[`apparmor/bwrap`](apparmor/bwrap) for `/usr/bin/bwrap`, following
[Ubuntu's bwrap guidance](https://discourse.ubuntu.com/t/understanding-apparmor-user-namespace-restriction/58007).
This permits namespace setup by the launcher while preserving the global host
restriction. Operators on such hosts should review and load the profile with
`sudo apparmor_parser --replace contracts/deploy/apparmor/bwrap` if the installed distribution
profile does not already permit setup. Callback filesystem, process, network,
resource and syscall restrictions remain enforced and tested.

The output directory must be new. CI clones the exact local commit into it,
installs the canonical locked SDK development environment with the contracts extra, and
checks a real isolated Python callback before native builds. If the host cannot
start the sandbox, `logs/callback-isolation.log` retains the bounded launcher
diagnostic from a fixed synthetic probe. No runtime sandbox or test is bypassed.
CI then runs format, compilation and tests for all three Elixir projects, Python runtime
and release-precondition checks, and the portable specification suite. It builds
two separate releases and requires identical manifests, file bytes, permissions
and commit timestamps, then exercises a copied wheel/engine installation. Every
command's real exit status and log path are retained in `result.json`; a failed
gate exits nonzero. The current-syntax v2, coordination and real HTTP schema
checkers are mandatory gates before release builds. Their coordination and HTTP
reports are written into the CI output directory, outside its tracked source
checkout; the tracked coordination reference is not regenerated by CI.
The selected Elixir/OTP installation and native sandbox
packages must already be installed. Network access to locked package sources is
needed. This command covers the standalone release. The separate Band database,
HTTP/WebSocket, system-manager and live-provider qualifications below remain
required for their respective deployment claims.

The build refuses to overwrite an existing release. It emits the engine, wheel,
contract examples, specification and fixtures, dependency locks, deployment
files and a SHA-256 file manifest with Git identity, toolchain and build policy. Record the
manifest hash when promoting a reviewed release. A manifest detects accidental
changes; authenticity comes from the trusted release distribution process.

The smoke check verifies file hashes, copies the bundle to an unrelated path,
installs the wheel into a fresh virtual environment, and uses only system tools
on `PATH`. It checks both current-profile contract header formats, private durable-room
restart/deduplication, the installed Python callback sandbox and Unicode files.

The engine's private pipe interface is:

```sh
/opt/contract-release/engine/bin/contract-engine /etc/contract-room/session.band frontmatter
```

Use `standard` for the skill-package adapter. Every qualification explicitly selects
`frontmatter` for `contracts/v2/hybrid-assistant.band` (0.2.0 with a contract clock);
the drills do not depend on the legacy 0.1.0 fixture. Band creates carry the exact
UTF-8 file-source object, and short-clock probes recompute its file hash. Paths are passed
as literal arguments, never interpolated into shell or Elixir expressions.
This pipe has host authority; expose the authenticated HTTP service to remote
participants. Room authority and remote local checking each own a separate
engine process. The wrapper disables Erlang distribution; supervisors own
process lifetime and restart.

Python embedding selects the installed executable explicitly:

```python
EngineProcess(
    contract,
    command=["/opt/contract-release/engine/bin/contract-engine"],
    format="frontmatter",
)
```

Development without `command` still uses the compiled source checkout.

## Service configuration and lifecycle

Install into a dedicated Python 3.12 virtual environment outside the sealed
release. Run this from the SDK root or the copied release root:

```sh
python3.12 -m venv /opt/contract/venv
python3.12 - <<'PY'
from pathlib import Path
from contracts.deploy.installation import install_release

install_release(Path("/path/to/release"), Path("/opt/contract/venv/bin/python"))
PY
```

The helper first verifies the release manifest, then installs the hash-locked
dependency wheels and canonical `band-sdk` wheel without index access and runs
`pip check`. It does not modify the sealed release tree.
Keep the environment at a stable path across compatible wheel upgrades. Copy
and edit `contracts/deploy/examples/room.json` or `agent.json`; their paths are illustrative.
The [configuration schema](../spec/schemas/service-config.schema.json) specifies
every field and bound. Unknown fields, explicit nulls, relative paths and shell
command strings are rejected. Commands are trusted absolute executable argv.

```sh
/opt/contract/venv/bin/contract-service check-config /etc/contract-room/service.json
/opt/contract/venv/bin/contract-service serve /etc/contract-room/service.json
```

`check-config` checks encoding and configuration semantics. Starting the service
also checks referenced files, credentials, identities, ownership, database
integrity and actual engine/program availability. Configuration and credential
files must be single-link regular files, owned by the service user (or readable
root-owned files), with mode 0600. Initial program source may be world-readable
but cannot be writable by other users. The service does not accept paths or
commands from an HTTP participant.

The HTTP `tokens_file` is a private JSON object mapping independently generated
bearer tokens (at least 32 characters) to `{actor,permissions}` grants. Permissions
are `room`, `events`, `controls` and `observe`. Agent `control_actors` additionally
limits each identity to named actions. Generate separate credentials for each
actor/service and provision them through your secret system. Never put tokens in
URLs, argv, examples or journals. `room.token` contains only the agent's room
bearer token. The provider receives its credentials through its private
environment. Child environments are allowlisted: engine, command-provider,
validator and generated-program children do not inherit those credentials.
Only the native OpenAI worker receives `OPENAI_API_KEY`; command integrations
cannot rely on ambient credentials or `HOME`.

Command providers and validators are operator-trusted integrations, not isolated
by environment allowlisting. If they run under the service's UID, they can still
read `provider.env` and `room.token` from disk whenever that UID has access,
including mode-0600 files owned by that UID. Use a separate UID and filesystem
access controls that deny credential-file access for untrusted integrations.
Generated programs use the separate sandbox boundary described in the
[remote runtime specification](../spec/remote-runtime.md).

The agent examples grant `wake`, `takeover` and `retry`, with repair disabled.
Before granting `resume` or enabling repair, configure a trusted, task-specific
`validator` command. Both routes replay accepted behavior and require that
validator's independent semantic checks before returning to program execution.

`examples/openai-agent.json` selects the native Responses provider. Set
`OPENAI_API_KEY` in the service's private environment (the supplied agent unit
reads `/etc/contract-agent/provider.env`). The credential is not accepted in
JSON configuration. The model, request/output caps and optional dated rate
policy are pinned configuration. The [provider binding](../spec/openai-provider.md)
defines request capture, uncertain failures and usage diagnostics. A rate policy
is an estimate input and must be checked for the chosen account/model. No rate
policy means cost is unknown. The adapter never retries a dispatched request by
itself; an uncertain result stays held for explicit reconciliation or retry.

Only an explicit `127.0.0.1` bind may omit TLS. Public binds require both
`tls_certificate` and a private `tls_key`; remote room URLs require HTTPS and
certificate/hostname verification. A private CA uses agent `room.ca_file`.
Credential/certificate rotation takes effect on restart and does not reset
accepted IDs, pending outbox entries, program state or call budgets.

The room polls timers even while idle and counts time spent offline. The agent
polls the durable room inbox, verifies each accepted fact, and advances its
durable cursor only after retaining the page. Redelivery uses accepted IDs.
Held unknown computations await explicit controls; polling does not repeatedly
invoke them. A retained room proposal is reconciled against the original ID and
its remaining send budget. Readiness includes engine health and the latest poll
fault; observer metrics expose polling faults and held work without payloads.

SIGINT/SIGTERM stop new work and drain admitted requests. A bounded callback may
finish and journal its output during shutdown, leaving its staged proposal for
restart. It is not resampled. The provider and quality validator are killable
command processes; the service does not configure unbounded Python callbacks.
The service closes the HTTP listener and workers before its store/engine. An
unclean supervisor kill remains recoverable through the same journal boundaries.

The supplied systemd units use separate Unix users/state directories, restart
limits, private temporary/device namespaces, filesystem restrictions and cgroup
resource caps. Provision `/opt/contract`, `/etc/contract-room` and
`/etc/contract-agent` before installing units. Do not share room and agent state
directories or enable namespace restrictions that prevent bubblewrap setup.
The room unit additionally blocks namespace creation, bounds syscalls to
`@system-service`, and protects kernel/control-group/clock/hostname settings.
Those room-only restrictions are not applied to the agent's bubblewrap setup.
The agent unit permits `AF_NETLINK` so bubblewrap can initialize its private
loopback device before generated code starts. Generated code still cannot create
any socket under the callback seccomp policy.
`KillMode=mixed` sends SIGTERM to the service supervisor first, allowing it to
retain bounded child results before closing its journal. At `TimeoutStopSec`,
systemd kills all remaining processes in the unit's cgroup.
Service units must be validated on the deployment host; their presence is not
proof that that host permits user namespaces or enforces every listed option.
Adjust `TimeoutStopSec` above the sum of configured model, remote request and
checker timeouts plus ingress/cleanup allowance (150 seconds covers the defaults).

For a host qualification using noninteractive sudo, run
`python3.12 -m contracts.deploy.qualifysystemd --release /absolute/release --state /new/private/check-directory`.
It verifies the sealed bundle, copies it under a unique `/opt` path, and runs the
unit protections through the actual system manager with the shipped static
`contract-room` and `contract-agent` users/groups, which must already exist and
have distinct non-root UIDs. The helper never creates accounts or injects
`DynamicUser`. It asserts every required effective protection with `systemctl
show`, plus kernel UID/GID, capabilities, memory/process limits, installed sandbox
denials, repair-result capture across shutdown, offline inbox recovery and room
receipt recovery. Credentials and model responses are synthetic. The helper
removes only its unique host paths and retains private logs/databases under the
chosen check directory. `--unit-directory` explicitly tests unpackaged templates
and is recorded as an override; final package checks omit that option.

The service configuration and generated program schema are pinned in durable
state. Provider/validator argv or behavioral configuration changes require an
explicit compatible migration; updating only HTTP credentials does not. Keep
old artifacts and backups until pending receipts are reconciled. Upgrade,
rollback and full qualification remain in `PRODUCTION.md`.

## Qualification against Band

The [Band binding](../spec/band-transport.md) specifies API routes, typed actors,
membership checks, atomic receipts, private projections and deadline handling.
Use `examples/band-agent.json` for the remote agent's `band-api-key` authentication.

`qualifyband.py` is a lab driver, not an installation command. It verifies and
copies a sealed release, installs the wheel in a fresh virtual environment, then
starts three real Band VMs on owned ports 4511–4513. It requires an isolated,
already migrated PostgreSQL database at
`127.0.0.1:5488/contract_prod20261010_test`, configured in the supplied platform
checkout with the `contractlab` user. The host helper parses the exact URL,
rejects query/fragment overrides, constructs a closed connection configuration,
and checks the installed Repo's effective target before starting the application.
It refuses any other database. The new `--state` directory
is private and retains fixture credentials and logs; never publish it.

```sh
python3.12 -m contracts.deploy.qualifyband --release /absolute/new-release \
  --platform /absolute/path/to/band-checkout --state /private/new-lab-directory
```

The harness confirms all three listeners, authenticated channel joins and the
actual node mesh. It exercises a 12-request duplicate race, role-private ordinary
room notifications, program/model routing, offline inbox, a lost accepted reply
followed by killing all three authorities, original-receipt recovery without
model resampling, current membership on every node and background expiry.
It uses a normal database pool with real commits and notifications. Band's test
feature grants are enabled and billing/Oban are disabled; provider answers are
scripted. Those boundaries are explicit in the
recorded result (`../agent-runtime/evidence/production-band-live.json`, historical artifact). Live model
quality, deployment-host validation and workload acceptance are separate gates.

## Qualification probe coverage

The Band driver uses two bound agent principals; a human owner is never a
contract role binding. It checks unbound room members and nonmembers on identity,
view, inbox and proposal routes on both authenticated API surfaces on each node
(48 denial probes), exact create retries, changed-config ID conflicts, cross-room
ID claims, and malformed view/inbox/source requests. Every contract response is
validated against the release's current-profile JSON Schemas; error responses
also have a strict status-specific shape. JSON Schema tooling is included in the
SDK's `contracts` extra and sealed in `requirements-runtime.lock`. The retained
`contracts/deploy/requirements-qualification.lock` records its historical input.
A passing unit/probe-oracle test is not a live Band qualification result.

The local command channel publishes private JSON atomically. Hosts retain
incomplete JSON for retry, publish the acknowledgement before deleting a command,
and do not repeat an already acknowledged membership operation after a crash.
