Architecture decision · a shared Rust core for every language SDK band-sdk-core v0.2.0 · 20 Aug 2026

Ship the protocol, not the plumbing.

One shared brain in Rust. Thin drivers, each in its own language — Python and TypeScript today, the native Rust client next, and any SDK that follows. The crate graph already draws this line; the bindings currently cross it in the wrong place.

Gavrie Philipson, based on input from and discussions with Amit Gazal, Nir Singher and Alexander Zaikman.

Vocabulary — so the rest reads without a Rust background

The words this argument turns on

A Band agent talks to the platform two ways: a long-lived WebSocket carrying live events — messages, participants joining, rooms appearing — and ordinary REST calls for everything else. The REST half is easy. The live half is not: connections drop, the backend restarts, a newer session supersedes an older one, and after every interruption the agent has to work out which rooms to re-subscribe to and what it missed. That recovery logic is the hardest code in an SDK, and today it exists three times over — by hand in Python, again in TypeScript, and a third time in Rust. band-sdk-core is meant to end that duplication. The question is how much of each SDK becomes Rust.

  • the line The split this deck is about: what is written once in Rust and shared, versus what each SDK keeps in its own language. Share too little and the duplication stays; share too much and the SDKs stop feeling like Python and TypeScript libraries. Two boundaries go by the name — this one, between Rust and the SDKs, and a second one inside the Rust core, between code that performs I/O and code that only decides. “Fix the line” later on is about the second.
  • host The program the Rust code is embedded into — the Python process running an agent, or the Node process. Not a server. “The host owns the socket” means Python or JavaScript opens and reads the connection, and Rust only advises.
  • sans-io French for “without I/O”: protocol code that touches nothing outside itself. It is told what arrived and returns a list of things it wants done — connect, send a heartbeat, close — for someone else to carry out. Any language can drive it; no network needed to test it.
  • protocol vs transport Protocol is what the messages mean and what to do about them. Transport is getting them across — opening the socket, writing bytes. The recommendation shares the first and not the second.
  • driver The loop that feeds the shared logic what happened and carries out the effects it returns. One per language, and each is thin — the whole effect vocabulary is four cases plus a timer.
  • FFI · binding · crate FFI is one language calling compiled code written in another; the “FFI boundary” is the line in concrete form. A binding is the glue implementing it. A crate is Rust's unit of packaging — roughly a package in Python, a module in npm.
  • runtime · asyncio · Tokio The scheduler that keeps thousands of operations in flight without a thread for each. asyncio is Python's, Tokio is Rust's. Both languages already have one, and they are not interchangeable — which is the whole cost of putting a second one in the host's process.
  • the GIL CPython's rule that only one thread may execute Python at a time. A Rust thread that wants to touch anything Python must take it first, and while it holds it the Python program is stopped. A free-threaded build without it is officially supported as of 3.14 — but it's a separate, opt-in interpreter, and the default build still has the GIL.
  • backpressure What a system does when data arrives faster than it can be consumed: slow the sender, buffer, or drop. Handing data between two runtimes forces that choice — in a place where “drop” means losing a user's message.
  • wasm vs NAPI Two ways to load compiled code into Node. NAPI is a real native binary — fast, unrestricted, one build per platform. wasm runs inside the JS engine — one artifact everywhere, but sandboxed: no sockets, no threads, no clock. Which one fits depends entirely on where the line sits.
  • wheel · the matrix A wheel is a prebuilt Python package. Today band-sdk ships one that installs anywhere; a compiled one must be built per OS × CPU × Python version. That matrix is the packaging cost of this decision.
  • drift One rule implemented separately in several places and gradually coming to disagree. It is the problem this project exists to solve, and there is already some of it in main.

On the wire, in passing: Phoenix Channels is the protocol the platform's Elixir backend speaks over the WebSocket, multiplexing many topics onto one connection; a close code is the number a WebSocket carries when it ends (1008 means stop, 1012/1013 mean the backend is restarting); backoff is waiting longer after each failed retry, with jitter so a fleet does not retry in lockstep.

The decision

Where the FFI boundary sits

Share core-protocol — the session state machine, reconnect planner, disconnect taxonomy, frame codec, rejoin policy. Everything sans-io. Every consumer drives it with its own transport, its own runtime, its own sockets.

The finding that reframes the question

We ship the cheap half, and none of the valuable half

REST is 83% of the Python binding and 78% of Node's — and nothing from core-protocol crosses at all. Meanwhile ~900 lines across the two SDKs re-implement what it already holds. The bindings export the layer with the least value per line, and none of the layer with the most.

REST — core-transport plus both bindings5,490 · 54% of the core
core-protocol — the layer worth sharing2,153 · crosses nothing
Protocol logic re-derived per language, in the SDKs929 · already drifted
And REST is the surface users touch most

It is also the single largest reclaimable investment in the repo — ~3,000 of core-transport's 4,831 lines, and ~80% of both bindings. The drift argument does not apply to it: REST is stateless request/response, and band-client-rest is already Fern-generated from the OpenAPI spec, which is a stronger single source of truth than a hand-written Rust client kept in step by hand. Routing it through Rust takes away httpx / fetch interceptors, proxy configuration, retry policies, custom timeouts and mock transports — the ordinary tools people reach for when dropping an SDK into an existing service.

Platform layers only — framework adapters and ~123k lines of Python tests are excluded, or they would bury the signal. And volume understates the risk: reconnect policy is 5 lines in Python against 353 in backoff.rs — the smallest gap on this table and the most operationally serious one in the review.

Why this line specifically

The drift we pay for is protocol drift, not socket drift

Nobody re-derives "open a TCP connection" wrongly twice. What does get re-derived wrongly: when is a session Up? Is this disconnect retryable? What's the backoff schedule? Does a deferred room_added survive a reconnect?

  • The SDKs stay native Host-owned sockets mean a stuck reconnect is diagnosable in the host's own tooling, a test can inject a fake transport, and transport logs obey BAND_LOG_*. Rust's tracing never reaches Python's logging.
  • Backpressure disappears Message payloads never cross. No bounded queue, no drop policy, and no CancelledError that has to reach a Tokio task as a silent drop.
  • Async bridging evaporates apply(input, now) → [effects] is synchronous and pure. No Rust runtime to own. Under this line there is no async bridge left to build.
  • Blast radius stays small A Python transport bug stays a Python bug, fixable by a Python engineer — not a Rust PR behind a four-repo release chain.
What “Rust owns transport” actually decides

Not Rust's async or Python's — one runtime or two

A Rust-owned socket puts a second I/O runtime inside the host process for the life of the program: Tokio's scheduler beside asyncio's loop, or Node's. Plenty of software does this and it works. But the costs sit in the seam between the two, they multiply rather than add, and none of them appear until production.

“Can a user set a breakpoint” is the wrong question — very little async debugging happens that way. The real one is whether an operator can reconstruct a stuck reconnect from what the process left behind. Tracing and spans answer that within one runtime, because a span tree encodes causality inside one scheduler. Two runtimes give you two span trees and a gap where the causal edge should be — and the gap is where cross-runtime bugs concentrate.

Reconnect policy is the strongest single argument here. It isn't hygiene — it's whether a fleet stampedes a recovering backend, and today the answer differs by language.

The other half of drawing a line

What we deliberately keep out — and how three drivers stay honest

A boundary is defined as much by what stays outside it. Three things read like candidates and are not, and naming them matters as much as naming the candidates — this is where “too much in Rust” gets stopped.

  • Phoenix framing Rust hand-rolls it in phoenix.rs because a native client must. Both SDKs already use mature libraries — phoenix-channels-python-client, phoenix.js. Replacing a working library with an FFI call is a pure loss.
  • Mention resolution Reads like protocol, isn't. It needs the participant roster — REST-derived SDK state — and its fallback rules are product behaviour, not wire contract. Exactly the “feels like a wrapper” boundary.
  • REST endpoint construction Codegen from the OpenAPI spec is the better single source of truth. endpoints.rs stays for the native Rust client and does not cross.
Before anything ships — the line inside the Rust core, not the one to the SDKs

Fix the line, then export it

About 520 of socket.rs's 1,811 lines (29%) aren't transport — they're pure decision logic sitting on the I/O side where no SDK can reach it. The prize is dispatch_frame, the 113-line frame router that decides what an inbound frame means — exactly what both SDKs hand-implement today.

End state: two crates, one rule

Does it perform I/O? No → core-protocol. Yes → core-transport. Fold room_watch in and dissolve core-runtime (186 lines that exist so two bindings can share one constant). The rule is mechanical and CI-checkable — the existing wasm32 gate enforces it, since sockets and Tokio can't compile there.

One discipline to hold

The moved code carries 10 tracing:: calls. core-protocol has zero and depends only on serde and serde_json. Writing a log line is I/O — so return diagnostics instead of emitting them, riding the return value the host already receives. No bridge, no queue, the wasm gate survives, and each SDK logs natively in its own words.

This is pure refactoring, in a private repo, with zero external consumers. It is the cheapest it will ever be.

Binding strategy

PyO3 for Python, wasm for TypeScript

Every front NAPI wins on — OS access, threads, zero-copy, Tokio — is a front core-protocol doesn't compete on. Wasm keeps the browser and edge paths open; a NAPI addon forecloses them permanently. For Python the asymmetry is the point: wasmtime-py is itself a per-platform compiled extension, so wasm deepens the wheel matrix rather than escaping it.

Measured, not assumed

The boundary's shape dominates the boundary's technology by 3–6×. Keeping payloads out entirely — only topic and event cross, a routing code comes back — costs 1.02–1.65× a bare JSON.parse and is identical between wasm and NAPI. It's both the fastest option and the one that makes the binding technology performance-neutral. Worst path measured still sustains ~154,000 frames/s on one core; Band runs at human chat rates. Decide this on architecture, not benchmarks.

Where an SDK stops feeling native

Errors have to land inside each SDK's hierarchy, not beside it

Both bindings collapse the entire taxonomy into one flat exception today — PyRuntimeError::new_err(e.to_string()) on one side, napi::Error::from_reason(e.to_string()) on the other. TransportError has eight variants, and the distinctions are exactly the operationally load-bearing ones:

Suppressed / Supersededterminal — stop
Disconnectedmay still reconnect
UpgradeRejectedcarries a retryability verdict
Apirequest_id, for backend logs

Flattened to a string, a caller recovers none of it except by matching on message text. And this gets worse under the recommendation rather than better: with the host owning transport, the host is what has to decide whether to reconnect.

  • Preserve the discriminant Whatever crosses must let a caller branch on which failure occurred without parsing a message. A subclass per group in Python; a discriminated union or code field in TypeScript — the shape disconnectReason.ts already uses.
  • Land inside the hierarchy, not beside it band-sdk-python already has BandError → BandConnectionError. A core failure should arrive as a subclass so existing except BandError handlers keep working. A bare RuntimeError from a Rust extension is the wrapper tell, where users meet it most.
  • Share the verdict, not the vocabulary Retryable vs terminal is a protocol fact and belongs in core-protocol. How it is spelled — exception class, error code, union tag — is idiomatic and belongs to each SDK.

Acceptable while the bindings have no consumers; not once an SDK depends on them. Under the narrow line the protocol surface itself raises very little — malformed frame, invalid state transition — so this is mostly about the errors each SDK's own transport raises, informed by one shared classification.

What we'd be accepting

Three real costs, worth naming out loud

  • A protocol hotfix stops being fast. Today a reconnect bug is one PR and one release. Afterwards: core PR → core release → dependency bump → SDK release → user upgrade. Five hops, four repos. Decide now whether that's acceptable for a Sev-1 — and keep an SDK-side override as the escape hatch. That hatch only exists because the SDKs keep their own transport.
  • Python stops being pure-Python. One universal wheel becomes a build matrix. Our CI is currently one cell — all three jobs on ubuntu-latest, no macOS, no Windows, no arm64, no musl. ABI3 collapses the CPython axis for the default GIL build; the platform axis has to be built out before Phase 3, not after.
  • Every SDK bug becomes potentially a Rust bug. The core repo is 11 days old: 53 commits, 42 from one author. This review is the second pair of eyes it was missing — what a review can't supply is a standing one, and once an SDK pins the core, every protocol fix needs a reviewer besides its author. Keep the core drivable from pytest, too, so a Python engineer can reproduce a protocol bug without a Rust toolchain.

The SDKs are maintained by a single developer today, and none of this is a criticism of that — a small team is part of why the repo is as coherent as it is. But these questions outlast whoever is answering them, and the team is likelier to grow than shrink, so they are stated in general terms.

Migration — each phase ships independently, both SDKs stay releasable

The path

  1. Fix the line. Stop growing the REST binding. Move the ~520 lines of policy into core-protocol, fold in room_watch, dissolve core-runtime. No behaviour change; wasm32 gate verifies it.
  2. Prove the pipeline. Export a trivial slice — topics, disconnect taxonomy — through PyO3 and wasm. Ship a real wheel and a real npm artifact end to end. De-risks packaging before any logic depends on it.
  3. Shadow mode in Python. Existing transport stays in charge, but also feeds the Rust machine and logs divergence. Nothing user-visible ships. This is what makes the migration safe.
  4. Cut Python over. Rust machine becomes the authority; delete duplicated decision logic from link.py and streaming/client.py. The SDK keeps its sockets, asyncio, logging, and test fakes.
  5. TypeScript, same path. Via wasm, reusing the shadow-mode approach.
  6. Native client. Consumes core-transport directly. Promote the shared scenario corpus to a gate across all three drivers.

Phases 0 and 1 are the ones worth starting now — both get more expensive with every week of binding growth.

For the room

What we need to settle

  • Does the TypeScript SDK need to run in a browser? Doesn't change the recommendation — wasm fits either way — but it changes how firmly we close the NAPI door.
  • Does the native client share the SDKs' semantics, or only the wire protocol? If it wants rooms, tools and adapters too, the shared surface grows and needs the same line-drawing discipline.
  • Is band-mcp a fourth consumer? It speaks the same protocol. The answer affects how general the shared surface should be.
  • Does core-protocol version separately from core-transport? release-please ships one version across all five manifests, so once the SDKs pin the core exactly, a transport-only fix for the native client churns their pin. Unified is simpler and the churn is cosmetic — but it is invisible until the first SDK pins, and much cheaper to change before that.
  • Who is on call for a core bug? The honest current answer is one person, and the escalation path is undefined.
Already settled — Gavrie, 17 Aug 2026

Mobile / React Native is not designed for upfront. Hermes — React Native's JavaScript engine, not the agent of the same name — has no wasm support, which is the one runtime gap. Safe to defer because core-protocol is sans-io: going native later is a second build target on unchanged source, not a rewrite. Trigger to revisit: a committed mobile or React Native client.

Adjacent — not architectural, worth a minute at the end

Four smaller things from the same review

Tracing — the two bindings disagree

  • Node hands each event to the host; Python prints it to stdout. initTracing(callback) crosses once per event, so its logs land in whatever logger the JS app already uses. Tracing() installs a Rust formatter filtered by RUST_LOG and crosses only at setup — no log line ever reaches Python.
  • A Python operator gets two disjoint logging systems. RUST_LOG and BAND_LOG_LEVEL don't know about each other, and Rust's output bypasses the configured file sink and rotation entirely. On this one axis Python is behind Node, despite being well ahead on REST and WebSocket coverage.
  • Both dissolve under the narrow line. If only core-protocol crosses and it returns diagnostics instead of logging them, there is nothing to bridge. Fix it only if core-transport stays exposed through a binding.

Tracing — no spans exist yet

  • All 21 call sites are flat events — no #[instrument], no info_span!, 19 of them in socket.rs and mostly warn!.
  • Node's binding has span machinery with nothing to flatten. Its doc comment names correlation_id, room_id and message_id as fields it merges — it reads as a description of current behaviour and is not one.
  • Instrument, reword, or delete. A connection-scoped span in core-transport is worth having either way — the native Rust client is a real consumer. The machinery in bindings/node has no consumer at all under the narrow line.

Tooling — the justfile

  • Right call over a make­file. No phony targets to maintain, and real parameter support — both things make would have charged us for.
  • The header comment is the honest one, and it's right. ci.yml re-types the recipes by hand and must be kept in sync; e2e-live.yml instead installs just and calls the recipe, and that lane is drift-proof for exactly that reason. The fix is already demonstrated inside the repo — adopt it in ci.yml: one setup step per job, and the sync burden retires.
  • Give just doctor a --fix. Today it reports a missing cargo-nextest or cargo-llvm-cov and leaves you to install it by hand. They're all one cargo install away, so --fix turns a diagnostic into onboarding.
  • Bare just should list the recipes. With no arguments it runs the first one in the file — currently doctor — so a newcomer typing just gets a toolchain check rather than a menu.

TypeScript — the Node pin

  • Why are we on Node 20? It's past end of life, and both workflows pin it — ci.yml and e2e-live.yml. We should be on 24 and/or 26.
  • The sharper problem is the mismatch. The addon is built and smoke-tested on a runtime the only SDK meant to consume it does not support, and the binding declares no floor at all:
band-sdk-core CI, both workflows20
band-sdk-typescript engines.node>=22.14.0
bindings/node/package.jsonno engines field
  • Compiling a NAPI addon against Node 20's ABI is not evidence it runs on what the consumer will. Moot for the SDK if wasm wins — wasm has no ABI coupling to a Node version — but it still applies to any native addon we ship, and to CI's ability to catch a regression at all.
